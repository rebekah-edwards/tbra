## Part 1 — Ship what's already fixed (closes 3 reports)

### What's in the tree

13 modified Swift files and 10 untracked ones. Verified 2026-08-15: `xcodegen generate` +
`xcodebuild -scheme Tbra` → **BUILD SUCCEEDED** (warnings only, all pre-existing iOS 26
deprecations). Also built for device and installed to Rebekah's phone via `push-to-phone.sh`.

**Bug fixes, each mapped to an open report:**

| Report id | Symptom | Fix in tree |
|---|---|---|
| `cb73411e-5a59-44ea-87c7-87e8301bcb4f` | Profile won't load in app | `ProfileView.swift` |
| `5a7145cd-4b85-4953-a2c7-b3919a8a6ae1` | Finish stuck in pending (`tf:AEH_mBUJuGDYsjDIqpStAuQ`) | `ReadingStateAlert.swift` + 16 call sites |
| `ba64c7cf-98b0-4da9-9d5f-537d484f4af2` | Spoiler sparkle missing | `SpoilerParticles.swift`, `ReviewsListView.swift` |

**Profile (`cb73411e`) — root cause, confirmed.** `ProfileView` had no `else` branch for the failed
load. The alert fires once, the reader taps OK (clearing `model.error`), and then
`data==nil / loading==false / error==nil` matches no branch — an empty scroll view, forever. `.task`
only runs on first appearance, so returning to the tab never retried. That is exactly the reporter's
"helped at first but then stopped allowing me to access the profile in app at all." The fix adds an
error state with a **Try again** button calling `model.load()`.

**Finish-pending (`5a7145cd`).** All 16 `setReadingState` call sites used `try?`, so a failed write was
indistinguishable from a successful one — the UI just kept showing the old state. They now route
through `ReadingStateAlert.shared.perform`, and `AppShell.swift` wires `.readingStateErrorAlert()`
into every full-screen cover. Note this makes the failure **visible**; if the underlying write is
still failing for that tester, they will now get an alert saying so, which is the information nobody
had. Watch for a follow-up report and treat it as new data, not a regression.

**Spoiler sparkle (`ba64c7cf`).** Implemented as its own `SpoilerParticles.swift`. It deliberately
diverges from web: the surface-alt chip behind the sparkle is **dark-mode only**, because the
particles are black in light mode and black-on-grey reads muddy. That divergence is intentional and
documented in the source — don't "fix" it to match web without asking.

### The complication: this is not only bug fixes

The untracked files also include an **entire widget extension** and a review-import feature:

```
native-ios/WidgetPublisher.swift      native-ios/Widgets/TbraWidgets.swift
native-ios/WidgetShared.swift         native-ios/Widgets/Info.plist
native-ios/WidgetPreviewHarness.swift native-ios/Widgets/TbraWidgets.entitlements
native-ios/ReviewImportSheet.swift    native-ios/ColorHex.swift
```

`AppShell.swift` also gained a private `tbra://` URL scheme for widget taps (AASA only covers
`/book/*` and `/u/*`, so widget deep links can't use universal links).

**This is the risk in the whole job.** Per memory `project_ios_status` / CLAUDE.md, the widget
extension **failed provisioning on 2026-08-13** and shipped a build that looked fine because the old
`.app` was still on disk. `push-to-phone.sh` was hardened for exactly that (it now trusts
`xcodebuild`'s exit code, not directory existence). A device build succeeding today does **not** mean
the widget will survive an App Store archive — archive provisioning is stricter.

**Recommended: decide with Rebekah whether the widget ships in this build.** The three bug fixes are
what the testers are waiting on. If the widget's provisioning isn't sorted, shipping the fixes without
it is the faster, lower-risk path and keeps a feature-sized unknown out of a bugfix release.

### How to ship

1. **Read `docs/ios-release-checklist.md` first.** Non-negotiable — `native-ios/project.pbxproj` is
   gitignored *and* regenerated by `xcodegen`, so any setting kept there silently reverts. Settings
   that must ship belong in `native-ios/project.yml`. This has already shipped a build with no app
   icon, a Release plist with `NSAllowsArbitraryLoads`, a no-op build-number bump, and an upload
   rejected for missing orientations.
2. Commit the native work. **Stage only the files you intend to ship** — never `git add -A`; the tree
   has unrelated dirt including `native-ios/DerivedData*`.
3. Bump the build number in `project.yml`.
4. Run `./native-ios/preflight-archive.sh <archive> <build#>` before every upload.
5. **Stable Xcode only** for the archive (`/Applications/Xcode.app`), not Xcode-beta —
   `push-to-phone.sh` uses beta, the release path must not. See `project_testflight_setup`.
6. Upload, then confirm with the testers before closing anything.

### Do not close the reports until testers have the build

A debug build on Rebekah's phone is **not** a TestFlight build. The three reporters still have the
broken app. Closing them earlier would be the precise failure the nightly triage task exists to
prevent — work marked delivered that no tester received. Verify in the DB when you do close them
(`feedback_triage_verification`).

## Part 2 — The two reports with no fix yet

Both are iOS, both from the same 2026-07-20 TestFlight batch, both **25 days old**. Neither could be
touched by the nightly task: the simulator tooling is **attended-session only** and refuses to run in
a scheduled task, so this needs a human-initiated session with a device or simulator.

### #4 Covers don't load in the library list — `2b67d3ea-ae5a-44a8-91c7-04855c9f62ad`

Tester's screenshot 3 shows the app *has* the cover; screenshot 1 shows the same book blank in the
list. So the URL is present and the image isn't rendering — a loading/caching problem in the list
view, not missing data. Look at the async image loading in `native-ios/LibraryView.swift` and its
shared cover view. Likely candidates: cache eviction under memory pressure, a cancelled task on fast
scroll, or no retry after a failed first load. Screenshots: `data/testflight-feedback/ACE_geJulYVUOGDE6svL9Ys-*.jpg`.

**This row is two reports in one.** Its other half — "title sort lumps all 'A …' titles together" —
was fixed by `3cc82a6` on 2026-07-30 and verified. **The row cannot close until covers is fixed.**

### #5 Search dropdown is clipped — `97ba7e21-71bd-44ac-85cc-697ebbbe3f0d`

From search results, opening the state dropdown cuts off the menu; the tester had to open each book
individually to reach the other options. Look at `native-ios/SearchView.swift` around the
state-setting call sites (~L392–418) and the menu container. Smells like frame/clipping or safe-area
on the row overlay rather than logic. Screenshot: `data/testflight-feedback/AMVpMk1BjVNKLvBsRDvFvBc-*.jpg`.
Cross-check `project_native_ios_kickoff` — the iOS 27 hit-testing bug family has overlapped with
"renders but can't be reached" before.
